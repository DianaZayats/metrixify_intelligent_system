# Відомі обмеження та ідеї на майбутнє

Фіксуються відомі обмеження, які **не блокують** демонстрацію MVP, але важливі під час перевірки або захисту.

## Витягування метрик

**Рейтинг «залітає» в продуктивність.** Якщо в одному повідомленні є «2 з 5» про самопочуття і згадка роботи/pet-проєкту, інколи та сама оцінка потрапляє в `main_job_productivity`. Очікування: лише `wellbeing`. Потрібно звуження scope у `metric-rating-parse` / промпті.

**Разовий забіг як звичка.** Фраза «вперше пробіг 20 хвилин» інколи стає стабільним фактом профілю про біг — фільтр `temporary` не завжди спрацьовує.

**Дрібний recall.** Дуже короткі симптом-записи інколи втрачають другорядну метрику; для дипломного MVP це прийнятно, але залишається простір для покращення промпту.

## Операційне

**Вартість OpenAI.** Не змодельована по `ai_runs`; для продакшену потрібна агрегація токенів.

**`npm run build` у backend.** Окремо `tsc` може скаржитися на старі типи, тоді як Vitest проходить — не критично для локального MVP.

**Persona CLI.** Повний `persona:analyze` на ~30 записах займає 13–15 хвилин послідовних викликів API; у CI за замовчуванням не використовується.

## Аналітика

**Кореляції не рахуються автоматично.** Потрібно натиснути **Analyze** на dashboard; для офіційного рівня — ≥14 парних календарних днів.

**Денна агрегація.** Події в межах одного дня зливаються (mean/sum/any true) — порядок у день не зберігається.

## Telegram / UI

**Голосові виправлення метрик** — не реалізовані (лише нові записи голосом).

**Inline URL на localhost** — Telegram не приймає; локально використовується `/login` або текст посилання.

**Дизайн-сторінка `/design-system`** — dev-огляд токенів; перед продакшеном можна прибрати з маршрутів.
