# Виправлення метрик через Telegram

Після завершення пайплайну бот надсилає список витягнутих метрик. Користувач може виправити дані **звичайним текстом** (краще відповіддю на це повідомлення). У веб-інтерфейсі також реалізовано редагування значення та дати спостереження на сторінці запису/метрики.

## Призначення

У щоденнику часто виникають помилки розпізнавання («не 2 хвилини, а 20», «це було вчора»). Окремі кнопки на кожен випадок не масштабуються — тому передбачено другий крок: LLM визначає **намір** → виконується команда → зміни записуються в БД з аудитом у `metadata_json`.

## Типовий сценарій

1. Користувач надсилає запис → пайплайн → `completed`.
2. Бот відповідає списком метрик (мова з `User.locale`).
3. Користувач пише виправлення (або відповідає на повідомлення бота).
4. Backend розпізнає команду, оновлює спостереження / визначення / запускає reprocess.
5. Бот підтверджує; для кореляцій можна підказати перерахувати вручну в UI.

## Підтримувані команди

| Намір | Приклад | Команда |
| --- | --- | --- |
| Змінити значення | «насправді 2 хвилини» | `fix_value` |
| Змінити дату | «це було сьогодні, не вчора» | `fix_observed_at` |
| Прибрати спостереження | «прибери цю метрику» | `remove_observation` |
| Додати | «снідав омлетом» | `add_observation` |
| Не відстежувати | «більше не відстежуй енергію» | `archive_metric` |
| Перевитягнути | «метрики не ті, переглянь ще раз» | `reprocess_entry` |

Голосом **нові** записи працюють; голосові **виправлення** поки не підключені.

## Аудит

У `metadata_json` спостереження:

- `source`: `user_correction`
- `editedVia`: `telegram`
- знімки `previous` / `new`
- за потреби `intentRaw`, `commandType`

## Формат відповіді бота (приклад)

```
✓ Запис збережено

Метрики:
• Горіхи — так (29 трав)
• Висип — 3/5 (29 трав)

Щоденник: …/journal
```
