# Технічне завдання на розробку MVP застосування для персонального щоденника, вилучення метрик і пошуку кореляцій

## 1. Призначення документа

Цей документ описує технічне завдання на розробку MVP додатку, яке приймає текстові та голосові повідомлення користувача через Telegram-бота, витягує з них структуровані метрики, зберігає вихідний текст, коротке резюме, персональний контекст користувача та створює веб-інтерфейс для аналізу динаміки метрик та пошуку кореляцій.

Цей документ я підготувала як технічне завдання для моєї дипломної розробки MVP локально розгортаного застосування зі зрозумілою архітектурою, суворою типізацією, документованим кодом та мінімальною кількістю лишньої сутності.

## 2. Короткий опис продукту

Програма працює як персональний інтелектуальний щоденник.

Користувач надсилає в Telegram-бот текст або голосове повідомлення. Система приймає повідомлення, при необхідності транскрибує голос у текст, зберігає вихідний текст, створює коротке резюме, витягує числові та категоріальні метрики, оновлює персональний контекст користувача та потім відображає дані у веб-додатку.

Головна MVP-фіча – пошук кореляцій між метриками користувача у часі.

Приклад:

Користувач пише або каже:

> Сьогодні прокинувся пізно і почував себе не дуже.

Система повинна:

1. Зберегти вихідний текст.
2. Створити короткий резюме.
3. Витягти метрику `wake_time_quality` або близьку за змістом метрику користувача.
4. Витягти метрику `wellbeing`.
5. Зберегти спостереження за дату.
6. Оновити профіль користувача з появою нових фактів.
7. Дозволити у веб-інтерфейсі побачити динаміку та можливі кореляції.

## 3. Мета MVP

Мета MVP - перевірити, що програма може стабільно виконувати повний цикл:

1. Прийняти введення користувача через Telegram.
2. Перетворити голос на текст.
3. Зберегти вихідний текст та коротке резюме.
4. Витягти метрики з неструктурованого тексту.
5. Динамічно створити або оновити користувацькі визначення метрик.
6. Зберегти спостереження за метриками.
7. Зберегти особисті факти користувача без дублювання.
8. Відобразити дані у веб-інтерфейсі.
9. Побудувати графіки за метриками.
10. Розрахувати базові кореляції між метриками.

## 4. Що входить до MVP

У MVP входять такі частини:

1. Telegram-бот для текстового та голосового введення.
2. Backend API на Node.js + TypeScript.
3. Черга фонових завдань обробки повідомлень.
4. Інтеграція з OpenAI API для транскрибації, резюмування та вилучення структурованих даних.
5. PostgreSQL-база даних з JSONB-полями та нормалізованим зберіганням спостережень.
6. Веб-додаток на Vue 3+TypeScript.
7. Авторизація у веб-додатку через Telegram-бота.
8. Дашборд із графіками.
9. Сторінка метрик.
10. Сторінка щоденникових записів.
11. Сторінка кореляцій.
12. Мінімальний екран профілю користувача із витягнутими фактами.
13. Docker Compose для локального запуску.
14. Документація англійською.
15. Автоматичні випробування для критичних модулів.

## 5. Що не входить до MVP

У MVP не входять:

1. Мобільний додаток.
2. Продакшн-хостинг.
3. CI/CD.
4. Платежі та передплати.
5. Багаторівнева рольова модель.
6. Адмін-панель для кількох користувачів.
7. Медичні діагнози та медичні рекомендації.
8. Автоматичні поради щодо лікування.
9. Складні прогнозні ML моделі.
10. Соціальні функції.
11. Громадські профілі.
12. Інтеграції з Apple Health, Google Fit, Garmin, Oura, Whoop та аналогічними сервісами.
13. Повноцінний no-code редактор схем метрик.
14. Ручна розмітка тренувальних датасетів.
15. Складна мультимовна локалізація інтерфейсу.

Важливо: MVP повинен бути достатнім для перевірки основної гіпотези, але не повинен перетворюватися на платформу з надмірною архітектурою.

## 6. Основні користувальницькі сценарії

### 6.1. Надсилання текстового повідомлення

1. Користувач відкриває Telegram-бота.
2. Користувач надсилає текстове повідомлення.
3. Робот підтверджує отримання.
4. Backend зберігає вихідне повідомлення.
5. Backend створює завдання на обробку.
6. AI-пайплайн витягує summary, метрики та факти.
7. Backend зберігає результат.
8. Користувач бачить дані у веб-інтерфейсі.

### 6.2. Надсилання голосового повідомлення

1. Користувач відправляє voice message у Telegram-бот.
2. Backend отримує Telegram update.
3. Backend завантажує аудіофайл через Telegram Bot API.
4. Backend відправляє аудіо в OpenAI transcription API.
5. Backend отримує текстову транскрипцію.
6. Backend зберігає транскрипцію як вихідний текст запису.
7. Далі запис проходитиме той самий пайплайн, як і текстове повідомлення.

### 6.3. Перегляд графіків

1. Користувач відкриває веб-програму.
2. Користувач авторизується через Telegram-бота.
3. Користувач потрапляє на Dashboard.
4. Dashboard показує останні записи, основні метрики та графіки.
5. Користувач відкриває конкретну метрику.
6. Система показує динаміку метрики щодня.

### 6.4. Перегляд кореляцій

1. Користувач відкриває сторінку Correlations.
2. Система показує таблицю або велику map кореляції між метриками.
3. Користувач вибирає пару метриків.
4. Система показує scatter plot, line chart та базові статистичні дані.
5. Інтерфейс явно показує, що кореляція означає причинно-наслідковий зв'язок.

### 6.5. Перегляд вихідних записів

1. Користувач відкриває сторінку Journal.
2. Відобразиться список усіх записів.
3. Відкриває конкретний запис.
4. Бачить:
   - raw text;
   - short summary;
   - extracted metrics;
   - extracted facts;
   - confidence score;
- Статус обробки.

## 7. Архітектурний принцип MVP

Головний архітектурний принцип: динамічна користувача структура даних не повинна реалізовуватися через створення нових таблиць, колонок або runtime-міграцій бази даних під шкірного користувача.

Для MVP використовується підхід:

1. Фізична структура бази даних є стабільною.
2. Динамічні схеми користувача зберігаються як дані.
3. Визначення метрик користувача зберігаються у таблиці `metric_definitions`.
4. Значення метрик зберігаються у таблиці metric_observations.
5. Персональні факти зберігаються у таблиці `profile_facts`.
6. Зміни схеми фіксуються через версійні записи.
7. AI не має права безпосередньо видаляти чи перезаписувати важливі дані.
8. AI формує пропозиції змін, а backend застосовує їх через валідовані операції.

Це дозволяє зберегти гнучкість без перетворення бази даних на некеровану систему.

## 8. Вибраний технологічний стек

### 8.1. Frontend

Використати:

1. Vue 3.
2. TypeScript.
3. Vite.
4. Pinia.
5. Vue Router.
6. TanStack Query для роботи із серверними даними.
7. ECharts для графіків.
8. Reka UI як headless component primitives.
9. Custom CSS variables для дизайн-токенів.
10. SCSS modules або scoped CSS для компонентних стилів.

Не використовувати Vuex.

Не використовувати Bootstrap.

Не використовувати готову візуальну дизайн-систему, що нав'язує зовнішній вигляд продукту.

Чи не будувати інтерфейс на голому наборі випадкових utility-класів. Визуальний шар повинен йти від Figma-токенів та компонентної системи.

### 8.2. Backend

Використати:

1. Node.js 22 LTS.
2. TypeScript.
3. Fastify.
4. Zod для runtime validation.
5. Prisma ORM.
6. PostgreSQL.
7. Redis.
8. BullMQ для фонових завдань.
9. OpenAPI specification для документування REST API.
10. Vitest для unit/integration tests.

### 8.3. Database

Використовувати PostgreSQL як базу даних.

Використовувати JSONB для динамічних частин схем, AI metadata, prompt payload snapshots і додаткових атрибутів.

Використовувати нормалізовані таблиці для:

1. користувачів;
2. повідомлень;
3. записів щоденника;
4. визначення метрик;
5. спостережень за метриками;
6. персональних фактів;
7. AI-запусків;
8. результатів кореляцій.

Використовувати pgvector для semantic retrieval за фактами користувача та memory chunks. У MVP pgvector потрібний не для складного AI, а для зниження витрат на LLM-контекст: система має знаходити релевантні фрагменти, а не надсилати моделі всю історію користувача.

### 8.4. AI providers

Використовувати OpenAI API для:

1. transcriptions;
2. structured extraction;
3. summarization;
4. schema resolving;
5. fact extraction;
6. embeddings для memory retrieval.

Усі AI-дзвінки мають проходити через єдиний backend-модуль `ai-gateway`.

Прямі дзвінки OpenAI із інших модулів заборонені.

## 9. Локальний запуск

Проект має запускатись локально однією командою.

Обов'язкові команди:

```bash
cp .env.example .env
npm run app:dev
```

Команда `npm run app:dev` повинна піднімати:

1. backend;
2. frontend;
3. PostgreSQL;
4. Redis;
5. worker;
6. Telegram bot polling process.

Для Docker Compose має бути команда:

```bash
docker compose up --build
```

У проекті має бути `README.md` з покроковою інструкцією для Windows, macOS та Linux.

Для користувача без технічної експертизи інструкція повинна пояснювати:

1. як встановити Docker Desktop;
2. як скопіювати `.env.example`;
3. куди вставити Telegram Bot Token;
4. куди вставити OpenAI API Key;
5. якою командою запустити проект;
6. де відкрити frontend;
7. як перевірити, що робота працює.

## 10. Авторизація через Telegram

Для MVP використовувати авторизацію через одноразове login-посилання, створене Telegram-ботом.

Причина: MVP повинен стабільно запускатись локально без продакшн-домена, HTTPS, налаштування Telegram Login Widget на домен та зовнішнього хостингу.

### 10.1. Login flow

1. Користувач пише `/login` у Telegram-бот.
2. Backend створює одноразовий login token.
3. Бот надсилає користувачеві посилання виду:

```text
http://localhost:5173/auth/telegram-token?token=...
```

4. Користувач відкриває посилання.
5. Frontend відправляє token на backend.
6. Backend перевіряє:
- Token існує;
- token не минув;
- token не був використаний раніше;
- token прив'язаний до Telegram user id.
7. Backend створює session.
8. Frontend зберігає session у httpOnly cookie.
9. Користувач потрапляє у веб-додаток.

### 10.2. Вимоги до безпеки login token

1. Token має жити 10 хвилин.
2. Token має бути одноразовим.
3. Token повинен зберігатися у базі лише у hashed form.
4. Після успішного використання token позначається як consumed.
5. Session cookie має бути httpOnly.
6. У development допускається `secure: false`.
7. У production-конфігурації cookie має бути `secure: true`.

## 11. Telegram-бот

### 11.1. Режим роботи

Для MVP бот працює у long polling mode.

Webhook mode не реалізується в MVP, тому що проект не планується хостити на сервері на етапі розробки MVP.

### 11.2. Команди бота

Бот повинен підтримувати команди:

```text
/start
/help
/login
/status
```

### 11.3. Поведінка бота

#### `/start`

Робот пояснює, що користувач може надсилати текстові та голосові записи.

#### `/help`

Робот показує коротку інструкцію:

1. відправь текст;
2. відправ голосове;
3. напиши `/login`, щоб відкрити веб-інтерфейс;
4. напиши `/status`, щоб перевірити обробку останніх записів.

#### `/login`

Бот генерує одноразове посилання для входу до веб-додатку.

#### `/status`

Бот показує статус останніх 5 записів:

1. received;
2. transcribing;
3. extracting;
4. completed;
5. failed.

### 11.4. Типи повідомлень, що підтримуються

MVP підтримує:

1. text message;
2. voice message.

MVP не підтримує:

1. image;
2. video;
3. documents;
4. stickers;
5. group chats;
6. inline mode.

## 12. Backend-модулі

Backend має бути поділено на наступні модулі.

### 12.1. `telegram-module`

Відповідає за:

1. прийом Telegram updates через polling;
2. обробку команд;
3. отримання text messages;
4. отримання voice messages;
5. завантаження voice files;
6. створення login tokens;
7. надсилання користувачеві статусів.

### 12.2. `auth-module`

Відповідає за:

1. перевірку Telegram login token;
2. створення session;
3. перевірку поточного користувача;
4. logout;
5. захист REST API endpoints.

### 12.3. `entries-module`

Відповідає за:

1. створення diary entries;
2. зберігання raw text;
3. зберігання short summary;
4. зберігання source type;
5. зберігання processing status;
6. отримання списку записів;
7. отримання деталей записи.

### 12.4. `transcription-module`

Відповідає за:

1. прийом audio file path;
2. відправлення файлу в OpenAI transcription API;
3. збереження транскрипції;
4. логування transcription run;
5. обробку помилок.

### 12.5. `ai-gateway-module`

Єдина точка доступу до OpenAI API.

Відповідає за:

1. вибір моделі;
2. складання prompt payload;
3. конвертацію JSON в TOON для LLM input;
4. виклик OpenAI API;
5. structured output validation;
6. retry policy;
7. token usage logging;
8. збереження snapshot входу та виходу;
9. нормалізацію помилок.

Жодний інший модуль не повинен безпосередньо імпортувати OpenAI SDK.

### 12.6. `summary-module`

Відповідає за створення короткої суми за кожним записом.

Summary має бути:

1. коротким;
2. нейтральним;
3. без медичних діагнозів;
4. без додавання фактів, яких немає у raw text;
5. придатний для швидкого перегляду в UI.

### 12.7. `metric-extraction-module`

Відповідає за витяг кандидатів метрик із тексту.

Модуль повинен витягувати:

1. назва метрики;
2. тип значення;
3. значення;
4. шкалу;
5. одиницю виміру;
6. confidence;
7. текстовий evidence span;
8. дату/період, до якого належить спостереження;
9. reasoning summary в короткій технічній формі.

Для довгих narrative-записів модуль повинен витягувати **декілька** метрик за різними подіями та контекстами, а не зводити день до 2–3 загальних шкал:

1. сон вночі / пробудження vs денний сон (boolean, тривалість, якість);
2. фізична активність (тривалість, якість, здоров'я після);
3. харчування (якість прийому їжі, сніданок);
4. продуктивність із поділом контексту (основна робота vs pet project), якщо користувач їх розрізняє.

Див prompt **v1.6.0** та fixture `output-rich-day-ru-01.json`.

Extraction використовує тільки analytics-ready типи (`number`, `ordinal`, `boolean`). AI не створює `category`.

Timeline:

1. `entry.recorded_at` передається у context pack;
2. LLM повертає `observed_at`, `observed_at_precision`, `narrative_order`, опціонально `observed_date`;
3. backend post-processing (`metric-candidate-normalize`, `metric-observed-at`, `metric-duration-parse`, …):
- recap: рівномірний розподіл `narrative_order` між 07:00 та `recorded_at` (TZ користувача);
- cross-day («вчора» + «сьогодні»): **не** recap; `observed_date` має пріоритет над narrative;
- nap: remap `sleep_quality` / помилковий fitness → `daytime_nap_*`; сума повторних сесій;
- junk-метрики без явного числа відфільтровуються;
4. precision і narrative order зберігаються в `metadata_json` observation.

Реалізовано API: `GET /api/metrics/observations` (всі observations користувача, опціонально `metricId=`).

Telegram feedback за створеними/оновленими метриками після Stage 8.

### 12.8. `metric-schema-module`

Відповідає за визначення користувача метрик.

Модуль винен:

1. шукати існуючу метрику по key, alias і semantic similarity;
2. визначати, чи можна прив'язати нове спостереження до існуючої метрики;
3. створювати нову metric definition за відсутності відповідної;
4. додавати або до існуючої метрики;
5. забороняти дублювання однакових метрик;
6. підтримувати soft archive метрик;
7. вести version history.

### 12.9. `profile-facts-module`

Відповідає за особистий контекст користувача.

Модуль винен:

1. отримувати факти про користувача;
2. не створювати дублі;
3. оновлювати існуючі факти під час уточнення;
4. зберігати історію змін;
5. зберігати evidence для кожного факту;
6. розрізняти стабільні факти та тимчасові стани.

Приклад стабільного факту:

```text
User works as a software developer.
```

Приклад тимчасового стану:

```text
User felt anxious today.
```

Тимчасові стани повинні зберігатись як entries/metrics, а не як постійний profile fact.

### 12.10. `memory-retrieval-module`

Відповідає за вибір релевантного контексту перед викликом AI.

Модуль винен:

1. знаходити релевантні metric definitions;
2. знаходити релевантні profile facts;
3. знаходити останні записи;
4. знаходити семантично схожі memory chunks;
5. збирати компактний context pack для LLM.

Модуль не повинен надсилати всю історію користувача LLM.

### 12.11. `analytics-module`

Відповідає за:

1. агрегацію оглядів по днях;
2. підготовку часових рядів;
3. розрахунок Pearson correlation;
4. розрахунок Spearman correlation;
5. розрахунок lag correlations;
6. збереження результатів;
7. Віддача даних frontend.

### 12.12. `documentation-module`

## 13. Формати даних: JSON та TOON

### 13.1. Головне правило

JSON є основним форматом даних усередині програми.

TOON використовується тільки як компактний формат передачі контексту LLM input.

### 13.2. Де використати JSON

JSON використовувати скрізь, де дані є source of truth:

1. REST API request/response.
2. Database JSONB fields.
3. OpenAPI schemas.
4. Zod schemas.
5. Frontend state.
6. Backend DTO.
7. Internal service contracts.
8. Test fixtures.
9. Structured Outputs from OpenAI.
10. Export/import data.
11. AI result validation.

### 13.3. Де використовувати TOON

TOON використовувати тільки в `ai-gateway-module` під час підготовки prompt input для LLM.

TOON підходить для:

1. список існуючих metric definitions;
2. списку абозборів;
3. компактний context pack;
4. останніх записів користувача;
5. видобутих profile facts;
6. memory chunks;
7. compact observation history;
8. prompt examples.

### 13.4. Де не використовувати TOON

TOON не використовуватиме:

1. зберігання у основі як основного формата;
2. REST API;
3. frontend state;
4. валідація результату моделі;
5. міграцій;
6. test assertions;
7. long-term audit data.

### 13.5. Вихід LLM

LLM повинен повертати результат у JSON через Structured Outputs.

Вихід моделі не повинен повертатися до TOON.

Причина: backend повинен валідувати результат через JSON Schema/Zod та безпечно застосовувати лише допустимі операції.

### 13.6. TOON codec

У проекті має бути окремий сервіс:

```text
llm-payload-codec
```

Він відповідає за:

1. конвертацію JSON context pack у TOON;
2. контроль версії формату;
3. snapshot підсумкового prompt input;
4. тести конвертації;
5. зворотна сумісність для старих AI run logs.

## 14. AI-пайплайн обробки запису

### 14.1. Загальна схема

Пайплайн обробки запису:

1. Receive input.
2. Create raw entry.
3. Transcribe audio when needed.
4. Normalize text.
5. Create short summary.
6. Build context pack.
7. Extract metric candidates.
8. Resolve metric definitions.
9. Save metric observations.
10. Extract profile facts.
11. Apply validated fact patches.
12. Create memory chunks.
13. Update embeddings.
14. Recalculate affected analytics.
15. Mark entry as completed.

### 14.2. Статуси обробки

Запис повинен мати статус:

```text
received
transcribing
transcribed
summarizing
extracting_metrics
resolving_schema
extracting_facts
saving_results
completed
failed
```

### 14.3. Idempotency

Кожен крок має бути ідепотентним.

Якщо worker перезапущено, повторна обробка повинна створювати дублі метрик та фактів.

Для цього використовувати:

1. `entry_id`;
2. `processing_step`;
3. `idempotency_key`;
4. unique constraints;
5. transaction boundaries.

## 16. AI safety та захист даних від пошкодження

### 16.1. AI не змінює дані безпосередньо

AI не повинен безпосередньо видаляти, перезаписувати чи мігрувати дані.

AI повертає лише структурований patch proposal.

Backend валідує patch proposal і застосовує лише дозволені операції.

### 16.2. Дозволені schema operations

Для metric schema дозволені операції:

```text
create_metric_definition
add_metric_alias
update_metric_description
archive_metric_definition
merge_metric_definitions
```

Для MVP автоматично застосовувати лише:

```text
create_metric_definition
add_metric_alias
update_metric_description
```

Операції `archive_metric_definition` та `merge_metric_definitions` повинні бути доступні лише через ручну дію користувача в UI.

### 16.3. Дозволені fact operations

Для profile facts дозволені операції:

```text
create_fact
update_fact
mark_fact_outdated
add_fact_evidence
```

AI може запропонувати операцію, але backend застосовує її лише після перевірки:

1. факт відноситься до користувача;
2. факт підтверджено фрагментом тексту;
3. факт перестав бути тимчасовим станом;
4. факт не дублює існуючий факт;
5. confidence вище мінімального порога.

### 16.4. Append-only audit log

Всі AI-рішення повинні зберігатися в `ai_runs`.

Для кожного AI run зберігати:

1. user_id;
2. entry_id;
3. prompt version;
4. model;
5. input token estimate;
6. output token estimate;
7. input snapshot;
8. output snapshot;
9. validation result;
10. applied operations;
11. created_at.

## 17. Cost optimization для OpenAI

MVP має бути спроектований так, щоб вартість обробки не росла лінійно від усієї історії користувача.

### 17.1. Заборонено

Заборонено:

1. відправляти всю історію користувача у кожен AI-запит;
2. надсилати всі raw entries за рік;
3. надсилати всі profile facts без фільтрації;
4. використовувати одну велику модель всім задач;
5. повторно транскрибувати вже оброблене аудіо;
6. повторно витягувати метрики із незміненого запису без необхідності;
7. використовувати LLM там, де досить deterministic logic.

### 17.2. Обов'язковий context pack

Перед AI-викликом система збирає compact context pack:

1. потоковий запис;
2. останні 5 записів користувача;
3. релевантні metric definitions;
4. релевантні абочовики;
5. релевантні profile facts;
6. релевантні memory chunks;
7. поточна дата та timezone користувача;
8. schema version.

### 17.3. LLM cascade

Обробка повинна йти каскадом:

1. deterministic preprocessing;
2. cheap model extraction;
3. backend validation;
4. stronger model only for ambiguous schema resolving;
5. no second AI call when first call gives valid high-confidence result.

### 17.4. Caching

У MVP використовувати кешування тільки в прикладних місцях:

1. embeddings для memory chunks;
2. context retrieval results на годину обробки одного запису;
3. resolved metric aliases;
4. prompt templates in memory.

Не робити складний глобальний cache layer для власних структур даних в MVP.

Причина: на етапі MVP це передчасна оптимізація. Основну економію дасть не кеш, а правильний context pack, нормалізоване зберігання та заборона відправлення всієї історії в LLM.

## 18. Метрики

### 18.1. Metric Definition

Metric Definition визначає, що саме вимірюється.

Поля:

```text
id
user_id
key
title
description
value_type
unit
scale_min
scale_max
positive_direction
aliases
tags
extraction_rules
created_by
created_from_entry_id
confidence
version
status
created_at
updated_at
```

### 18.2. Value types

`value_type` описує **формат значення observation**, а не тематику метрики в житті користувача.

Підтримувати типи:

```text
number
ordinal
boolean
category
```

- `number` - кількість або вимір (7.5 hours, 2 cups).
- `ordinal` - суб'єктивна шкала (зазвичай 1-5).
- `boolean` - так/ні.
- `category` - **номінальне текстове значення** observation (наприклад тип тренування = "running"). Це не life-domain категорія.

### 18.2.1. Tags (life domains)

Metric Definition може мати **кілька tags** — тематичних міток для групування та фільтрації в UI:

```text
sleep
mood
energy
mental-health
fitness
nutrition
work
productivity
social
routine
health
habits
```

Правила:

1. Tags зберігаються в `tags_json` (масив slug-рядок).
2. AI при extraction повинен пропонувати 1-4 tags на нову метрику.
3. Користувач може редагувати tags вручну.
4. Tags не замінюють `value_type` і не дублюють `aliases`.
5. При schema resolving tags зливаються при link/merge (union, dedupe).

Для кореляцій MVP використовувати тільки:

```text
number
ordinal
boolean
```

`category` зберігається, відображається в UI, але не бере участь у кореляціях MVP. Не плутати із life-domain **tags**.

### 18.3. Metric Observation

Metric Observation – конкретне значення метрики в конкретний момент чи період.

Поля:

```text
id
user_id
entry_id
metric_definition_id
observed_at
period_start
period_end
value_number
value_text
value_boolean
confidence
evidence_text
source
created_at
updated_at
```

### 18.4. Нормалізація шкал

Для метрики якості використовувати шкалу 1-5.

Приклад:

```text
1 = very bad
2 = bad
3 = neutral / not good
4 = good
5 = excellent
```

Для кількісних метрик використовувати фактичні значення:

```text

coffee_cups = 2
wake_time_hour = 10.75
```

### 18.5. Приклад вилучення

Input:

```text

```

Expected metrics:

## 20. Кореляції

### 20.1. Призначення

Модуль кореляцій повинен знаходити статистичні зв'язки між метриками користувача.

Система має стверджувати причинно-наслідковий зв'язок.

### 20.2. Підтримувані методи MVP

У MVP реалізувати:

1. Pearson correlation.
2. Spearman correlation.
3. Same-day correlation.
4. Lag correlation на -1 день та +1 день.

### 20.3. Мінімальні вимоги до даних

Кореляцію вважати лише за наявності щонайменше 14 парних спостережень.

Відображати надійність результату:

```text
low sample: 14–19 paired observations
medium sample: 20–39 paired observations
higher sample: 40+ paired observations
```

### 20.4. Correlation Result

Поля:

```text
id
user_id
metric_a_id
metric_b_id
method
lag_days
sample_size
correlation_value
p_value
strength_label
calculated_at
```

### 20.5. Strength labels

Використати:

```text
very weak
weak
moderate
strong
very strong
```

### 20.6. UI-попередження

На сторінці кореляцій обов'язково показувати текст:

```text
Correlation does not prove causation. Use this as a signal for further observation, not as a medical or behavioral diagnosis.
```

Додатково показувати, що Stage 10a використовує **денну агрегацію** (§20.7): події всередині одного дня усереднюються/сумуються.

### 20.7. Денна агрегація (Stage 10a)

Перед розрахунком кореляцій кожна метрика перетворюється на **одне значення на календарний день** (timezone користувача):

| value_type | Правило |
| --- | --- |
| ordinal | середнє протягом дня |
| number | сума протягом дня |
| boolean | true, якщо хоча б одне true протягом дня |

Декілька обстежень в один день (наприклад, добрепочинаючи після їжі) беруть участь через ці правила, а не як окремі точки кореляції.

### 20.8. Розширення після Stage 10a (не блокують MVP)

1. **Event-level co-occurrence** для boolean-метрик з урахуванням порядку `observed_at` усередині дня (наприклад "орехи → висип").
2. **Insights LLM** — інтерпретація знайдених кореляцій з урахуванням profile facts та memory chunks; окремий етап **після Stage 11**, не змішувати із Stage 10a.

### 20.9. Перерахунок analytics

У MVP користувач запускає перерахунок по кнопці в UI (`POST /api/analytics/recalculate`) з loading state. Результати зберігаються в `correlation_results`.

## 24. Обробка помилок

### 24.1. Telegram помилки

При помилці обробки повідомлення бот повинен відповісти:

```text
I received your message, but processing failed. You can try again or check the web app status page.
```

Помилка має бути збережена в `diary_entries.processing_error`.

### 24.2. AI помилки

AI помилки не повинні ламати весь процес.

При помилці AI:

1. entry отримує статус `failed`;
2. помилка зберігається в `ai_runs`;
3. користувач бачить статус failed;
4. UI дає кнопку `Reprocess`.

### 24.3. Partial processing

Якщо transcription пройшла успішно, але extraction впав, transcript має зберегтися.

Якщо сума створена, але metrics extraction впала, summary повинна зберегтися.

Система повинна втрачати проміжні результати.

## 26. Вимоги до коду

### 26.1. Головний принцип

Код повинен бути зрозумілим, прямим і читаним для junior developer після короткого онбордингу.

Не потрібно писати код так, ніби проєкт одразу розрахований на велику команду інженерів.

### 26.2. TypeScript

1. Використовувати strict TypeScript.
2. Заборонити `any` без технічного коментаря.
3. Використовувати Zod для runtime validation зовнішніх даних.
4. Використовувати типи Prisma для DB layer.
5. Не дублювати типи вручну, якщо їх можна вивести зі схеми.
6. Для громадських сервісних методів використовувати явні return types.

### 26.3. Простота замість зайвих абстракцій

Заборонено:

1. створювати абстрактні заводи без реальної необхідності;
2. створювати generic repository layer поверх Prisma без причини;
3. використовувати ув'язнення для бізнес-логіки;
4. створювати `BaseService`, якщо не вирішує конкретну проблему;
5. робити premature plugin architecture;
6. виносити кожен рядок у helper;
7. створювати універсальні функції, що використовуються один раз;
8. додавати мікробібліотеки для однієї функції;
9. використовувати складні паттерни там, де є досить звичайній функції.

### 26.4. Допустимий стиль коду

1. Використовувати early return.
2. Тримати функції короткими.
3. Розділяти pure logic і side effects.
4. Називати змінні за змістом.
5. Використовувати прості перетворення типів.
6. Використовувати `+value` для очевидного numeric cast у локальному контексті.
7. Використовувати `Number(value)` там, де важливою є явність для валідації зовнішнього введення.
8. Не змішувати parsing, validation та business logic в одній функції.

### 26.5. Коментарі

Коментарі потрібні задля переказу коду, а пояснення рішень.

Погано:

```ts
// increment counter
counter++
```

Добре:

```ts
// Telegram may deliver the same update twice, so this key prevents duplicate entries.
const idempotencyKey = buildTelegramUpdateKey(update)
```

## 33. Критичні архітектурні рішення

### 33.1. Dynamic schema as data

схеми користувача метрик зберігаються як дані в metric_definitions, а не як структура бази даних.

### 33.2. JSON as source of truth

JSON використовується у внутрішній логіці, API, базі, тестах та OpenAI structured outputs.

### 33.3. TOON only for LLM input

TOON використовується тільки для компактної передачі context pack LLM.

### 33.4. AI proposes, backend validates

AI не змінює дані безпосередньо. Backend застосовує лише валідовані операції.

### 33.5. Local-first MVP

MVP оптимізовано під локальний запуск без CI/CD та хостингу.

### 33.6. Telegram login token instead of Telegram Login Widget

Для MVP використовується login token через Telegram-бота, тому що це стабільно працює локально.

### 33.7. Queue-based processing

Обробка повідомлень йде через чергу, щоб Telegram bot та API не зависали на довгих AI-дзвінках.

### 33.8. Documentation-first delivery

Код, модулі, prompts, база та запуск мають бути документовані англійською мовою.

## 34. Ризики MVP

### 34.1. Дублювання метрик

Ризик: AI буде створювати різні метрики для подібних смислів.

Контроль:

1. aliases;
2. semantic retrieval;
3. schema resolver;
4. manual merge у UI;
5. tests на типові кейси.

### 34.2. Зростання вартості OpenAI

Ризик: обробка стане дорогою за довгої історії користувача.

Контроль:

1. context pack;
2. TOON input;
3. embeddings retrieval;
4. cascade model strategy;
5. AI run token logging;
6. заборона відправлення всієї історії.

### 34.3. Невірні метрики

Ризик: AI помилково оцінить суб'єктивний стан.

Контроль:

1. confidence;
2. evidence text;
3. manual correction;
4. reprocess;
5. clear UI visibility.

### 34.4. Хибні кореляції

Ризик: Користувач прийме випадкову кореляцію за причинність.

Контроль:

1. minimum sample size;
2. sample quality labels;
3. causation warning;
4. display raw observations;
5. no medical claims.

### 34.5. Втрата контексту при оновленні profile facts

Ризик: новий факт перезапише старий факт.

Контроль:

1. append-only evidence;
2. version history;
3. status instead of delete;
4. backend patch validation.
